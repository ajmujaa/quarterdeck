Security

Quarterdeck can start agents and run commands on your machine, so this page says plainly what protects you, what has been tested and what has not.

What it never collects

  • Keystrokes
  • Screenshots or screen contents
  • Which apps or websites you use
  • The clipboard
  • Your location
  • Any file outside the projects you register and its own data folder

It also changes nothing without a click or an explicit --apply, and sends your data nowhere except the request you asked for. A test scans the code for the programming interfaces that would collect any of the above.

How it stays safe

  • The model thinks, the harness acts. A review call gets read-only search and read tools limited to its working folder, and no shell, no git and no gh. A builder call can also edit files inside a throwaway working copy and run a few named commands (npm run, node, python3, pytest). The harness alone commits, pushes and posts, and only with an explicit apply.
  • The dashboard is local. It binds to 127.0.0.1 only, pairs through a one-time link that works once and for five minutes, and checks a session token and a same-origin test on every change.
  • Private places are closed to models. Your data folder's private files, ~/.ssh, ~/.aws, ~/.config and other credential places are on a deny list.
  • Outgoing text is scanned for credentials and refused on a hit. This is a safety net for accidents, not a barrier against someone determined.
  • Project commands run in a sandbox. Your project's test and build commands run with a minimal environment and a scratch home folder. On macOS they run inside sandbox-exec, with writes only in the worktree and the network limited to this machine. An install step is the exception and has network access. On Linux they use bubblewrap, which has so far run only in the project's own CI.
  • Model-made changes to sensitive files are refused before any project command runs: CI files, dependency manifests, test-runner configs, .env files and similar.
  • Text from a pull request, an issue or a web page is data, never instructions.
  • Credentials you enter for connections are kept in a private file on your computer (mode 0600), or on macOS optionally in the Keychain, which protects less than it may seem (see the security notes on GitHub).

What is tested

  • A self-test suite, run with python3 bin/selftest.py, also run in CI on macOS and Ubuntu.
  • Prompt injection: 50 hostile texts in 16 styles, tested offline, and 701 real runs on two models in which none obeyed (plus 400 control runs with the protection removed on purpose, in which 2 obeyed). A few dozen texts are not a proof, and results vary by model and by run.
  • Third-party files in the dashboard are pinned by checksum and checked on every self-test.

What is not tested, or not yet

  • The Linux sandbox has run in CI only. Project commands on Linux go through bubblewrap (bwrap) or are refused. It was written on a Mac and its own notes list it as unverified on real Linux machines, in containers and on distributions that restrict user namespaces.
  • Cloud packs are experimental. The six infrastructure packs were tested on small examples only.
  • No specialist security review yet. The protections above come from the project's own tests and rounds of self-audit, not from an outside expert.
  • On macOS, sandbox-exec is deprecated by Apple.
  • The few shell commands a builder model runs fall under the Claude Code command-line tool's own sandbox, which this project did not change or test.
  • Another web server on 127.0.0.1 that you browse to can receive the dashboard's session cookie and read (not write) the dashboard until the session ends.

The full lists, with the reasoning, are in SECURITY.md and THREAT-MODEL.md.

Reporting a problem

Use GitHub's private vulnerability reporting: the Security tab of the repository, then Report a vulnerability. Please do not open a public issue for a vulnerability. We aim to acknowledge a report within a few days and to say what we will do about it.
